## Findings

### 1. The NLRB walk keeps no failure and no by-day limit: every company in a run asks again, and a by-day "newest" read can take 300 pages every hour · `P2`

**How sure:** high. This is the repository's own `walkNlrb` running on PostgreSQL 16 with migrations to db/055, called once per "company" as `scripts/ingest.ts:903` calls it, with a stubbed `fetchPage`.

**Evidence**
- **The walk runs once per company.** It is called inside each company's `run("nlrb_decisions", …)` (`scripts/ingest.ts:902–906`).
  - The only thing shared across those calls is the process budget, `nlrbBudget = { left: 300 }` (`lib/ingest/nlrbWalk.ts:25,32`).
  - The pause between pages applies only within one walk: `if (gapMs && walk.pages) await sleep(gapMs)` (`:71`). Each company's first request waits for nothing.
- **A failure is not recorded anywhere the next company reads.**
  - In newest mode, a failed page returns at once: `if (got.outcome !== "ok") return failed(got, …)` (`:114`).
  - Nothing is written to `nlrb_reads`; only a `throttled` page in list mode sets `refused_at` (`:94`).
  - `shouldBackOff` holds an `error` back for that subject alone (`lib/ingest/store.ts:768–783`).
  - `loadLastFetched` counts only `ok` and `empty`, so the source stays due.
- **Which answers are errors.** An HTTP 500, 502 or 504, a timeout (90 s, `lib/nlrbDecisions.ts:329`), and a page with no listing (`:335`). check:nlrb pins a 200 "Access Denied" page as an `error`, not a refusal (`scripts/check-nlrb.ts:414–426`).
- **The newest read pages on until it meets a kept decision.**
  - The loop breaks only on `got.rows < 100 || got.decisions.some((d) => known.has(d.document))` (`:116`).
  - When the budget runs out it returns "this run's pages are spent" (`:112`) without writing the `newest` row, so the next run starts again. There is no night-window check on this path.
- **Harness, real Postgres, one process, 200 calls:**
  - By day, with page 0 answering an error: **200 requests, 200 failures**, budget 100 left.
  - At night, during the first whole read, with page 5 failing: **300 requests** (148 of them the failing page, 152 re-reads of page 4). The `partial` row is left at `next_page 5`, `refused_at` null.
  - By day (17:00 UTC), with the listing held, the `list` row two days old, and pages of 100 rows whose document links the parser no longer reads: **300 pages in run 1 and 300 again in run 2**, the `newest` row never written.

**Failure scenario**
- The NLRB changes its document link form (the parser's `document\.aspx\/([0-9a-f]+)`, `lib/nlrbDecisions.ts:95`) or its table markup.
  - Each hourly refresh then reads 300 listing pages in business hours: about 7,200 a day, ten times the whole listing.
  - The NLRB's policy asks bulk reads to be "scheduled for non-peak hours (between 11pm EST – 6am EST)", and its firewall refused the night read at page 340 (batch 162).
- A host that stops answering costs each company 90 s. A default refresh of 200 companies (`scripts/refresh.ts`, run hourly per `docs/OWNER-ACTIONS.md:73`) then spends about 5 hours on one source. This is the OCC failure the 2026-11-16 audit's finding 2 described and batch 155 fixed for the OCC alone.

**What a fix would need:**
- Keep a failed walk as the process's answer, as `cachedOccList` now does.
- Write a by-day read's outcome (or a back-off) into `nlrb_reads`.
- Cap the newest read at a few pages, and treat a page of rows that yields no decision as an error.

*Importance:* medium to high: no wrong row, but sustained peak-hour bulk reads against a site with a stated policy and a firewall that already refused us · *Efficiency:* a few lines in `walkNlrb` · *Practicality:* easy.

### 2. Batch 163's mappings make two pages store the same filing rows: each ingest retitles about 2,300 (AA and HWM) and 3,800 (DD and EIDP) rows with its own company's name · `P2`

**How sure:** high. The upsert below was reproduced on PostgreSQL 16.

**Evidence**
- **The reader titles a predecessor's filing with the page's name.**
  - It reads the predecessor's record as `recordFilings({ ...company, cik }, …)`, keeping the successor's name (`lib/sec.ts:1165–1167`).
  - A filing's title is `` `${company.name}: ${label}` `` (`:1011`) and its identity is `sec:${accession}` (`:1023`).
- **Both pages now ingest the same records.**
  - Old Alcoa's record 4281 is HWM's own ("Howmet Aerospace Inc.") and AA's predecessor ("Alcoa Corp").
  - Old du Pont's record 30554 is CTA-PA's and CTA-PB's own ("EIDP, Inc.") and DD's predecessor ("DuPont de Nemours, Inc."), all in `data/edgar-tickers.json`.
  - Filings carry no first-price floor, so both pages store all of them (the ledger: 2,297 and 3,819 before the handover days).
  - `listedAs` (`lib/predecessors.ts:308–331`) is the first mapping of a record that is also a page; check:predecessors forbade it until batch 163.
- **The upsert overwrites the title.** On a dedup-key conflict it sets `title = EXCLUDED.title` whenever the content hash differs, and the title is part of that hash (`lib/ingest/store.ts:1187, 1215–1229`).
  - `loadEvents` shows `r.title` as stored (`lib/store/read.ts:281`). Only `OWN_RECORD_FROM` and fund series are retitled when a page reads its rows, and neither covers these records.
- **Harness.** `upsertEvent` of accession 0000004281-94-000005 as AA's reader titles it, then as HWM's:
  - after AA's ingest: one row, `'Alcoa Corp: Annual report (10-K)'`, on subject 1;
  - after HWM's: one row, `'Howmet Aerospace Inc.: Annual report (10-K)'`, on subjects 1 and 2.
- **What the check pins.** check:predecessors asserts only what `getFilingsDeep` returns ("titled as Alcoa's"), never the stored row after the other page's ingest.

**Failure scenario:**
- After HWM's next filings refresh (every 6 hours, `lib/ingest/refresh.ts:25`), AA's page lists old Alcoa's 1994–2016 10-Ks, 10-Qs and earnings 8-Ks as "Howmet Aerospace Inc.: …".
- After AA's refresh, HWM's page shows its own record's filings as "Alcoa Corp: …".
- DD and CTA-PA/CTA-PB swap "DuPont de Nemours, Inc.: …" and "EIDP, Inc.: …" the same way.
- Each ingest rewrites thousands of rows that the last one wrote.

**What a fix would need:** for records with `listedAs`, title the shared filing at read time by the page's subject (as `asOwnSeriesFiling` does for fund siblings), or store a title that is not one page's name.

*Importance:* medium: the wrong company's name on thousands of rows on four large pages, flipping several times a day · *Efficiency:* one read-time rule · *Practicality:* moderate.

## Set aside (9)

1. **The night window is checked once per walk.** Nothing stops a run's 300 pages at 6 am Eastern, but at the measured 5.4 s a page a run takes about 27 minutes, inside the 45-minute room. Only a much slower site would overrun, and none was observed.
2. **Soft navigation can leave an old focus.** `useState(initialFocus)` and the mount effect keyed on `filterKey` (`components/CompanyExplorer.tsx:84, 90–114`) would keep an old focus if the same path were reached again with a new `?focus=`. No in-app link does that today: `SearchBox` is only on the home and not-found pages, and BestMatches and FocusBar carry no focus links. No reachable path.
3. **The migrations lock pages while they rebuild the index.** db/053 and db/054 each `DROP INDEX` and `CREATE INDEX` in one transaction, so `event_attestations` is under ACCESS EXCLUSIVE until the GIN build commits, and page reads wait during `db:migrate`. A pause at deploy time, not a wrong page; OWNER-ACTIONS says it "takes a moment".
4. **"A page before" on resume is more than growth at the listing's head needs.** It is harmless: one page read again a run.
5. **The 'partial' row's `decisions` overcounts re-read pages.** The `list` row is written from `count(*)`, so nothing shown is wrong.
6. **"11pm EST" is read as Eastern local time** (America/New_York, so EDT in summer). A stated choice (batch 161's ledger).
7. **The NLRB rule rescans every stored decision per company.** Each company's ingest loads all of them (33,989 in the fixture): 120–300 ms a company here, about double after the whole read. Acceptable.
8. **DD's Digest mapping is not exercised.** The 1985 fixture holds no du Pont entry; the one-claimant code applies to it as to AA.
9. **GE's Wabtec-era certification stays off GE.** "GE Transportation, A WABTEC Company" (2021-02-07) is no longer GE's, and nothing reads it as GE's.
