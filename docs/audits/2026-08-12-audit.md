## Findings

### 1. The Internet Archive query sorts date-ascending on a false premise, so it selects mis-catalogued items and can never reach recent material · `P1`

**Evidence:** `lib/archive.ts:109-111` justifies the sort — *"archive.org items carry catalogued metadata rather than OCR guesses, so the oldest hits are genuinely the oldest"* — and `lib/archive.ts:119` sets `sort[]=date asc`.

Live, through `fetchArchiveItems` itself:

| query | items | date range | pre-1900 |
|---|---|---|---|
| `"Ford Motor"` (9,808 upstream matches) | 48 | **1770 → 1916** | 12 |
| `"Nvidia"` (founded 1993) | 50 | **1898 → 1999** | 1 |
| `"Alibaba Group"` | 49 | 2014 → 2020 | 0 |

Raw payload for the oldest `"Ford Motor"` hits — five Driscoll sheet-music covers, all 1914–1929 songs stamped `year: 1770`:

```
{"date":"0001-01-01T00:00:00Z","identifier":"energy-invention-suppression","year":1}
{"date":"1292-01-01T00:00:00Z","identifier":"TheInternationalJew_201709","year":1292}
{"date":"1770-01-01T00:00:00Z","title":"The Little Ford Rambled Right Along","year":1770}
```

**What is wrong:** Mis-catalogued dates are not "a rarity" in this dataset — they are exactly what a `date asc` sort promotes to the top. Roughly half the request budget is spent on items the ingest floor immediately discards, and because the 50 oldest are always the subject's earliest years, the archive contribution to a company page is **permanently frozen in its first few years**. It cannot ever return a post-1998 NVIDIA item, a post-1980 Apple item, or a post-1915 Ford item.

**Why it matters:** This is the source `lib/archive.ts:6-8` calls *"structurally safe"* — keyless, no licence risk, the intended backbone of the 1963–2017 coverage gap. Nothing offline can see the problem, because `check:archive` (52 cases) tests parsing, not the query.

**Suggested fix:** Stop sorting by date. Chronicling America already made this call correctly for the same reason; if a date window is wanted, ask for it in `q` rather than by taking the head of an ascending sort.
*Importance:* high · *Efficiency:* high · *Practicality:* high.

### 2. Aave's Snapshot space id is not a Snapshot space, so `/topic/aave` can never carry a governance event · `P1`

**Evidence:** `lib/onchain/governance.ts:45-50` registers `space: "aave.eth"`. Against `hub.snapshot.org`:

```
{ space(id: "aave.eth")    } -> {"data":{"space":null}}
{ space(id: "aavedao.eth") } -> {"data":{"space":{"id":"aavedao.eth","name":"Aave DAO","proposalsCount":970}}}
```

Running the repo's own `fetchGovernance` against `aavedao.eth` returns 10/10 parsed events immediately.

**What is wrong:** `aave.eth` has never existed on Snapshot. Aave's DAO space is `aavedao.eth`.

**Why it matters:** This is precisely the failure `lib/onchain/governance.ts:34-36` predicts about itself — *"A wrong space id returns an empty proposal list, which on a page is indistinguishable from 'this protocol has not voted lately'."* The page has shipped an empty timeline since 2026-07-28, and the mechanism built to make the zero visible (per-space reporting in `check:feeds`) has been printing that zero without anyone reading it.

It also makes one line of the checklist wrong: the 2026-08-12 live-verification table records *"Snapshot ✓ (40 proposals)"*. That was one of two configured spaces; the other is dead.

**Suggested fix:** Change the id to `aavedao.eth`, and have `check:governance` assert every id in `GOVERNANCE_SPACES` resolves to a non-null `space` — a one-request live assertion, not a fixture.
*Importance:* high · *Efficiency:* very high — one string · *Practicality:* very high.

### 3. Two ingest branches apply no plausibility floor to archive items at all · `P1`

**Evidence:** `scripts/ingest.ts:403-406` (company path, no founding year) passes archive items straight through with only `.slice(0, 25)`, under a comment asserting *"a wrong date is a rarity there"*. `scripts/ingest.ts:285` computes `const floor = firstEventOn ? Number(firstEventOn.slice(0, 4)) : 0` — and a floor of `0` filters nothing.

The only remaining guard is `okYear = y >= 1500` inside `parseArchiveDate`, which admits the 1770 and 1812 items measured in finding 1.

**Why it matters:** The checklist states the standard for exactly this: *"being wrong doesn't throw: it plants an event in the Middle Ages, drags the timeline's range with it, and leaves a page that looks fine to anyone not reading the axis."* A 1770 sheet-music cover on Ford's timeline does all three, and drags the chart domain back 133 years.

**Suggested fix:** Give the archive branch an absolute floor when no subject-derived one exists. Both branches want the same rule.
*Importance:* high · *Efficiency:* high · *Practicality:* high — one shared constant.

### 4. "Site that day" links promise a capture that does not exist, on every event row · `P1`

**Evidence:** `components/EventList.tsx:745` and `:770` render `SiteSnapshotLink` with **no date gate**, labelled `site that day ↗` and titled *"See {domain} as it looked around {date}"*. The URL is built blind at `lib/wikidata.ts:36`.

Asking the archive what a 1926 Ford link actually resolves to:

```
GET https://archive.org/wayback/available?url=ford.com&timestamp=19260101
-> closest capture: 19981202213531
```

**What is wrong:** Wayback redirects to the *nearest* capture, so a link labelled "as it looked around 1926" lands on a page captured in **December 1998**. Every event row before ~1996 carries this link, and it cannot be right for any of them.

**Why it matters:** The product argument is that a date on screen is a claim the reader can check. `lib/wikidata.ts:32-34` states the design assumption, which is true about the mechanism and false about the label built on it.

This also **corrects a recorded item**: the checklist says of `fetchSiteSnapshots` that *"this function has no production caller… Either the snapshot strip gets built or the function goes."* A snapshot surface does ship — `SiteSnapshotLink`, on every row with a `site_domain` — it just does not consult the function that would tell it whether a capture exists.

**Suggested fix:** Suppress the link when the event predates the domain's earliest capture, or restate the label as the nearest available capture with its own date. The verifying function already exists and is fully checked.
*Importance:* moderate-high · *Efficiency:* high · *Practicality:* high.

### 5. "3M" resolves to nothing — the prefix rung's length guard blocks a unique match · `P2`

**Evidence:** `lib/sec.ts:137-141` gates the name-prefix rung on `q.length >= 3`. Live: `3M -> null`, while `MMM -> "3M CO"`. `3M` is not a ticker and the title is `3M CO`, so only the prefix rung could answer.

Measured against the committed index: the prefix `"3M "` matches **exactly one row**. Across the file, 140 distinct two-character title prefixes exist and **94 are unique**.

**What is wrong:** The guard's stated reason (*"guards against junk prefixes"*) is a length rule standing in for an ambiguity rule. It costs a Dow 30 component its own everyday name, and the visitor is told *"That didn't match a listed security."*

**Suggested fix:** Gate the prefix rung on how many rows the prefix matches, not on how many characters were typed. The count is available in the local index at no cost. Adjacent to the tracked `P1` "Score candidates instead of laddering" but does not need it.
*Importance:* moderate · *Efficiency:* high · *Practicality:* high, entirely local.

### 6. Ethereum milestone rows credit an explorer that answered nothing · `P2`

**Evidence:** `lib/onchain/ethereum.ts:85-88` sets `sourceLabel: "Blockscout · Etherscan"` unconditionally, on both the chain-read branch and the `fallbackDate` branch. From this container `eth.blockscout.com` returns `403 Host not in allowlist`, yet `getEthereumMilestones()` still returns four fully-formed events, every one labelled `Blockscout · Etherscan`.

**What is wrong:** When Blockscout is unreachable the code substitutes the curated `fallbackDate` — deliberate and documented — but the row's provenance does not change. It still tells the reader the date was read from Blockscout.

**Why it matters:** The repo's standard is that a failed provider degrades with *visible* provenance, and this is the event kind whose entire justification is that an `onchain` row carries proof a reader can re-verify.

**Suggested fix:** Carry the label from whichever branch produced the date.
*Importance:* moderate · *Efficiency:* high — one variable · *Practicality:* high.

### 7. `npm run check:feeds` does not exercise three of the sources the release gate names · `P2`

**Evidence:** The ⛔ gate names *"SEC filings, Federal Register, prices"* among what must be checked. `scripts/check-feeds.ts:128-161` never calls `getFilings`, `fetchRegulations`, `getDailyPrices`, `getBitcoinHalvings` or `getEthereumMilestones`.

The report warns against over-reading a green line; it does not say which lines are absent, and absence is harder to notice.

*Importance:* moderate — it is the gate's instrument · *Efficiency:* high · *Practicality:* high.

### 10. `lib/signals.ts` computes displayed figures with no check of any kind · `P2`

**Evidence:** Production consumers: `app/api/signals/route.ts`, `components/SignalPanel.tsx`, `lib/enrich/explain.ts`. No `check:signals` exists. Its four numeric helpers — `median`, `mad`, `isSpike`, `weekEnd` — are **module-private**, so no offline check could reach them even if written.

One behaviour visible from reading it: at exactly two members, `median` is the midpoint of the pair, so both are equidistant and `worst` is decided by sort stability — i.e. by database row order. A two-company group reports *"A outran by X"* or *"B lagged by X"* arbitrarily.

**Why it matters:** Every comparable pure-arithmetic module here has a suite — markers, dates, refresh, cost, relevance, sentiment, compare. This one produces the numbers most likely to be read as a finding about a company, and it is the exception.

**Suggested fix:** Export the four helpers and add `check:signals`, covering the spike threshold, the zero-spread arm, and the two-member divergence case.
*Importance:* moderate · *Efficiency:* moderate — needs a small refactor · *Practicality:* moderate.
