## Findings

### 1. The commercial licence gate fails open on the scheduled refresh path · `P1`

**Evidence:**
`lib/ingest/store.ts:243-249`:
```ts
export async function assertCommercialOk(client: PoolClient, key: SourceKey): Promise<void> {
  const { rows } = await client.query<{ commercial_ok: boolean }>(
    "SELECT commercial_ok FROM sources WHERE key = $1",
    [key]
  );
  if (rows[0] && !rows[0].commercial_ok) {
```
When no `sources` row matches, `rows[0]` is `undefined`, the condition is false, and ingest proceeds.

The rows come from `ensureSources` (`lib/ingest/store.ts:190`). Its only three callers:
```
$ grep -rn "ensureSources" scripts lib app
scripts/seed-demo.ts:22 / :354
scripts/ingest.ts:8 / :347
scripts/plan.ts:8 / :142
lib/ingest/store.ts:190:export async function ensureSources(...)
```
`scripts/refresh.ts` is not among them. It imports the ingesters directly —
`scripts/refresh.ts:25: import { ingestCompany, ingestTopic } from "./ingest";` — and calls them at
`scripts/refresh.ts:70-71` and `:97-98`. `scripts/ingest.ts:347` seeds the table in its own CLI
`main`, which the refresh path does not enter.

No migration seeds the table either:
```
$ grep -rln "INSERT INTO sources" db/
(no output)
```

**What is wrong:** On a database where `ingest.ts`'s CLI main, `seed-demo` or `plan` has never run,
the scheduled refresh ingests with the licence check silently permitting every source — including
the eight flagged `commercialOk: false` at `lib/ingest/store.ts:73,82,91,100,109,118,127,136`. The
check does not error, log, or skip; it returns normally.

**Why it matters:** The project's stated policy is that a source whose terms bar commercial use
must not be reachable from a production path. `MASTER-CHECKLIST.md:129` already tracks turning
`COMMERCIAL_MODE=true` on the day the site earns money; that flag guards `licensedKey`, but
`assertCommercialOk` is the independent DB-side gate, and a gate that returns "fine" for a source
it has never heard of provides no defence in depth. The failure is silent, so nothing in
`source_fetches` would show it happened.

**Suggested fix:** Treat a missing `sources` row as a refusal rather than a pass, and have the
refresh path establish the registry before ingesting.
*Importance:* high — licensing exposure, silent · *Efficiency:* high — a one-condition change plus
one call · *Practicality:* high — no schema or interface change.

### 2. `servedFrom: "live"` is unreachable, but the badge and README still promise it · `P2`

**Evidence:** `lib/page-data.ts:17` declares `export type ServedFrom = "database" | "live";`, but
the only two assignments in the file are `servedFrom: "database"` at `lib/page-data.ts:76` and
`lib/page-data.ts:110`. The file fetches nothing — its imports (`lib/page-data.ts:1-5`) are
`react`'s `cache`, `./store/read`, `./types`, `./ingest/queue`, `./history`.

`components/ServedFrom.tsx:3-6` still describes itself as:
```
 * Small honesty badge: whether this render came out of the database or had to hit
 * the upstream APIs. Also the quickest way to see the read-through cache working.
```
and `components/ServedFrom.tsx:10-23` still renders the dead arm with the tooltip
`"Fetched live from the sources and stored for next time"`. It is rendered on both detail pages:
`app/company/[ticker]/page.tsx:69` and `app/topic/[slug]/page.tsx:59`.

`README.md:392-395` still documents the deleted behaviour: *"`lib/page-data.ts` is a **read-through
cache**. A page tries the database first; on a miss or a stale subject (6h for topics, 1h for
companies) it fetches live, renders, *and* stores what it fetched … A small `stored` / `live` badge
on each page shows which path served it."*

**What is wrong:** Commit `813d505` removed live fetching from the render path but left the
two-valued type, the component's dead branch, and the README paragraph. Every page now renders
`stored`, unconditionally.

**Why it matters:** This is a provenance badge — a surface whose whole purpose is telling the
reader something was checked. A badge with exactly one reachable value implies a comparison the
code no longer performs, which is the same class of over-claim the project's own comment at
`components/ServedFrom.tsx:3` calls an "honesty badge". `tsc` cannot catch it: an unused union
member is legal.

**Suggested fix:** Decide whether the distinction still exists. If it does not, collapse the type
and either drop the badge or restate it as what it now is; either way the README paragraph has to
follow.

> **Prior-work disclosure:** `docs/PRELIMINARY-FINDINGS-2026-07-30.md` lists, under *Reported, not
> verified*, that "README.md reportedly still describes `lib/page-data.ts` as a read-through cache
> with `stored`/`live` badges (deleted by `813d505`)". The README half of this finding is therefore
> a **re-derivation, not a new observation** — I confirmed it with my own citation above. What is
> new here is the unreachable `"live"` arm of the exported type and the fact that the badge is
> still mounted on two live routes.

*Importance:* low-moderate — misleading, not wrong-numbered · *Efficiency:* high — deletion, mostly
· *Practicality:* high, but needs an owner decision on intent first.
